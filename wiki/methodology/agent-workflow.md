## Overview

Both successful projects use the same loop: **inventory → mirror → difftest → state property → prove/refute → reproduce → independent review**. Only reviewed rows count as progress. Agents work in parallel, each in its own module, merged through a gate. This is the protocol adopted (adapted) in this repo's `AGENTS.md`.

## Loop per function

1. **Inventory row** exists for the function (`todo | modelled | excluded`, exclusions with a reason prefix).
2. **Mirror** the Scala body line by line, cite `path:line` at the pinned tag.
3. **Difftest** to 100% on many seeds (see [Differential testing](differential-testing.md)).
4. **State** a property from a law, Scaladoc, docs or an obvious invariant; quantify over all inputs/schedules; hypotheses only documented preconditions. Smoke-test it (Plausible / real CE) first.
5. **Prove** (`x_proven : P`) or **refute** (`x_refuted : ¬P` + bug record + reproducer that prints `REPRODUCED <id>`). Never weaken. Hard → `open` with a note.
6. **Review** by a different agent that only reads.

## Review rubric (adapted from both projects)

Three questions per modelled row; FAITHFUL only if all are yes, else HOLLOW; when unsure answer no:

1. **MIRROR** — does the proposition use a Lean function mirroring *this* body (branches, checks, loops, calls in the same order), not a hand-written spec or a bare variable? Are citations right?
2. **PROPERTY** — does it state a promised behaviour, quantified over all allowed inputs (and schedules), with only documented preconditions?
3. **SETTLED** — proven, or refuted with a bug record and reproducer?

Excluded rows: does the reason truly apply? Extra checks:
- **Wrong-function test**: would `fun _ => .error`, "always succeed", or "never run finalizers" also satisfy it? Then HOLLOW.
- **Vacuous hypotheses**: does a hypothesis assume the interesting case away ("not cancelled", "index in bounds")? julia: 128 of 130 quick proofs did.

## Known failure patterns (avoid)

Breadth-first thin properties (<50% survived review); success-path-only models; missing re-entrancy; callbacks as plain lists; `rfl` on one-liners; examples instead of quantification; bugs in internal helpers unreachable from the public API; stubbing definitions; editing statements.

## Bug records and filing

- One YAML per defect: id, title, priority, kind, area, files, functions, summary, likelihood, `maybe_intended`, reproducer, output per version, expected, `promised_by`, cause, possible_fix, duplicates (with recorded search queries), lean property/theorem.
- Exotic-input rule: also state the ordinary-case property.
- Flip on fix: after an upstream fix, re-mirror and prove the *same* statement.
- **Project decision (user, 2026-11-10): never open bugs, PRs, comments or reactions in any repository other than this one** (including `typelevel/cats-effect`). Bug records stay in this repo. Read-only `gh` on other repos is fine. (The precedents filed upstream after human review; we do not.)

## Orchestration (python-formalization)

Subagents in git worktrees (`worktree-agent-<hex>`), one module each (this repo, Phase 6: each agent merges `origin/main` into its branch before its final report, and has its own bug-id and codec-namespace range; see [Phase 6 merge notes](../../raw/project-decisions/2026-11-10-phase6-merge-notes.md)); merge gate rejects files outside the module; review verdicts on main win conflicts; a lock serializes merges; every merge reruns all difftests and reproducers; heavy builds on a separate big machine with a memory watchdog.

## Satisfiable hypotheses (decision 53, added 2026-11-10)

A statement whose hypotheses never hold together is vacuous: it is HOLLOW (review batch 4: `Bracket.MarkersOnly`). Every property with a non-trivial hypothesis set needs a Lean witness: one concrete input that meets all hypotheses and reaches the interesting case. Smoke tests must evaluate the hypotheses too. Test markers capture a handle that only the harness holds (decision 54). Batch 6: the check must also see handles and names inside closure fields that hold other closure ids, and numbers that the runtime computes (clock); a "pass on what you got" escape clause is unsafe when data numbers can be ids. Source: [decision 53](../../raw/project-decisions/2026-11-10-decision-53-satisfiability.md).

## Reviewer evidence (added 2026-11-10)

A reviewer cites only evidence it opened: a wrong-function test, a witness or a fixed twin counts only if the reviewer found the file and the declaration. A doc comment that names a check is not evidence (review batch 4 relied on a file that did not exist; [note](../../raw/project-decisions/2026-11-10-reviewer-evidence-rule.md)).

## Fixed-twin check for refutations (added 2026-11-10)

A refutation is HOLLOW when a correct implementation also refutes the statement (review batch 2 found this twice: a model artifact made `¬P` true for every implementation). For each refutation, mirror the upstream fix or the `possible_fix` as a twin, and show on a bounded domain that the twin satisfies the property.

## Harness privacy (decision 56, added 2026-11-14)

Three review rounds (batches 4–6) each found a new marker forgery. Patching each found forgery did not converge. Rule: harness tokens must be private by construction, or a kernel-checked lemma must show that user steps preserve privacy. No escape clauses; runtime numbers (clock) are user data. One shared module owns this for all tracks. Each known forgery becomes a Lean regression `example`. Source: [decision 56](../../raw/project-decisions/2026-11-14-decision-56-harness-privacy.md). Implementation (track Res): `Props/Phase6/HarnessPrivacy.lean` (tokens = harness cells allocated first; events capture them; codes are token names; `UserPrivate`), `WellFormed` `Lib.fields` (deep `captured`), regressions in `Proofs/Phase6/PrivacyExamples.lean`; see [Resource use, allocated, both](../cats-effect/resource-use-both-model.md). A probe lemma is only as wide as its environment and samples.

Review batch 9: decision 58 closed closure names, but the `Resource` mirror still names `REnv` table entries by data numbers (`RelFn.const k`), and a data source code (`USrc`) runs them. Rule: every decoder that turns data into a program or a table lookup is a name; it needs the same capability rule. Source: [review batch 9 notes](../../raw/project-decisions/2026-11-15-review-batch-9-notes.md).

## Wrong-function battery (decision 63, added 2026-11-15)

Three review findings (batches 11b, 12) were operations that always raise and still satisfied every statement. Rule: for each structure, the registered statements together must reject, per public operation, the variants raises, hangs, drops and doubles, each kernel-checked on one input, with a table in the notes. Safety statements need a companion success claim. Source: [decision 63](../../raw/project-decisions/2026-11-15-decision-63-wrong-function-battery.md). Review batch 13 added: (a) for a try-operation the "drops" variant is the honest one (answers `false` / `None` with no effect); (b) the battery includes the factories; (c) a success claim conditioned on "the root is done" must also claim that the root `Succeeded`, or a raising factory meets it ([notes](../../raw/project-decisions/2026-11-15-review-batch-13-notes.md)).

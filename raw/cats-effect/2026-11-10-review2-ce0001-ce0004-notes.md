## Decision 37: poll values are opaque (`WellFormed` clause 6)

- `progOK` allows `UnmaskRunLoop(p, m, s)` only with `m ≠ 0` and a held poll `(m, s)`. User code builds `UnmaskRunLoop` only through `IO.applyPoll` with a real poll; `IdPoll` (`Val.poll 0 0`) is the identity.
- `WF.PollOpaque env`: for every renaming `σ` of poll handles that keeps mask id 0, `env.callV (rnId σ id) (rnVal σ arg) (rnView σ v) = rnResult σ (env.callV id arg v)` for each even id. `rnId` renames the polls in the captured values of a closure id (the codec stores captures in the id). `rnIO` maps `UnmaskRunLoop(p, m, s)` to `IO.applyPoll (rnIO p) (σ m s)`. A renaming of a real poll to `IdPoll` is allowed, so a body cannot tell `IdPoll` from the run loop's poll.
- Why Scala cannot break it: `Poll[F]` is a trait with only `apply`; the `IOFiber` poll and `IdPoll` are anonymous classes in private code. Only reflection or `Object` methods (`eq`, `hashCode`, `toString`, `getClass`) can tell polls apart.
- Helper: `WF.pollOpaque_of_const` proves the clause for user code that ignores its argument and view (fixed result per id, poll-free closure values). `WF.rnFn_user_of_all`, `WF.rnId_of_all` take a decidable hypothesis.
- What it breaks: `Proofs/Calibration/ResourceEval.lean` (`r_wellFormed`, CE-0002, not edited by this change). Tested fix (compiles against this branch):

## Decision 38: CE-0001 for non-fatal errors; CE-0004

- New CE-0001 statement: hypotheses `WellFormed` (with clause 6) and `NonFatalOnly env fa` (`progNonFatal` on the start program and on every user program; every user throw non-fatal). Observations are compared after `eraseObs` (every poll value replaced by `Val.poll 0 0`): the run loop and `syncStep` give the body different `Poll` objects by design, and a program can return or emit its poll.
- The witness (case 4) is unchanged and needs no error at all (`cx_nonFatal`).
- CE-0004: `IOFiber.scala:263-269` calls `onFatalFailure` for `Error(fatal)` (added by PR #3811 for issue #3767, merged into `series/3.5.x` 2023-11-23). `SyncIO.scala:257-259` has no check. Public-API difference: `sio = SyncIO.raiseError(fatal).handleErrorWith(_ => SyncIO.pure(1))`: `sio.unsafeRunSync()` = 1, `sio.to[IO].syncStep(Int.MaxValue).unsafeRunSync()` = `Right(1)`, `sio.to[IO].unsafeRunSync()` throws the fatal error (runtime shut down). Same output on 3.7.1, `series/3.x` (de84c01) and `series/3.7.x` (2f94201).
- Only one fatal `IO` run per JVM is observable (by reading `IOFiber.scala:1597-1646`; not run): after the first, `IORuntime.globalFatalFailureHandled` is set, and `onFatalFailure` only rethrows on the worker thread (no callback), so a second `unsafeRunSync` would hang. The reproducer runs the `IO` side once and last.
- History: #549 (2019): maintainers said fatal errors are out of the laws ("all bets are off"; `IO(throw e) <-> IO.raiseError(e)` only for non-fatal `e`). #3767/#3811 (2023) then made `IO.raiseError(fatal)` fatal; neither mentions `SyncIO`. Duplicate searches found no issue about `SyncIO` and fatal errors.
- Lean: `raiseErrorTwin` (for every `e`, `IO.raiseError(e).handleErrorWith(_ => IO.pure(1))` satisfies `StepIdentityFor`), refuted with a fatal `e` (direct: `fatal e`; stepped: `Succeeded(1)`). Fixed twin `SyncIOEnv.fixFatalRaise := true` (the `SyncIO` `Error` branch throws a fatal error out of `unsafeRunSync`) holds for `e` in {fatal 0, fatal 5, nonFatal 0, interrupted 0}; v3.7.1 holds for the non-fatal two. The general non-fatal version (`raiseErrorTwinNonFatal`) is open: `decide` cannot check a free error code.

## Decision 39: fixed twins

- `Proofs/Calibration/StepCheck.lean`: a finite check for `StepIdentityFor`. Facts: fuel below `F` gives no claim; fuel `m + F` gives the same rest (`rfl` with free `m`); state lists from `grow` are closed under both `step` choices; all claim states have one erased observation. `stepIdentity_of_check` and `not_stepIdentity_of_check` (and `'` variants with a computed rest).
- PR #4700 (read 2026-11-10): `DeferredPoll` whose `poll(io)` is `IO.Local(Unmask).flatten` (reads the real `Poll` bound in the fiber's `IOLocal` state; `null` → `io` unchanged); `Uncancelable(body)` → body gets the `DeferredPoll`, in a `try` (non-fatal throw → `raiseError`), rest `Uncancelable(Bind(deferred, rest))`; `Bind(poll)` = `local.getAndSet(poll).flatMap(prev => (rest.attempt <* restore).rethrow)`; a rebuilt `Uncancelable(Bind)` is walked directly; `FlatMap(Local(Unmask), _)` walks `ioc` and rewraps; `OnCancel` rewraps with `onCancel(fin)`; changed cases use `stepsUntilDefer - 1`. `IOFiber` is not changed.
- Twin model: `DeferredPoll` = `Val.poll 0 (d + 1)` with `d` a fresh `Deferred` cell id; `IOLocal` state = list of `(d, poll)`; closures `FixLam` (library ids, namespace 9) capture programs through `ioV` (a program as a `Val`); `applyPollT` is `Poll.apply` for all three poll kinds. The model's `IO.Local` returns a `Val`, so `Unmask(...).flatten` is `Local(unmask d).flatMap(applyK ioc)`.
- Result on 10 non-fatal programs (`SyncStepTwinFamily.lean`): the twin satisfies `StepIdentityFor` on all 10; v3.7.1 fails programs 1, 4, 5, 6, 10 and passes 2, 3, 7, 8, 9. The reviewer's suspicion (a fix that keeps `IdPoll` in the continuation is wrong for a poll after an async boundary) is right for such a fix but not for PR #4700: programs 2, 5, 6, 7 apply a poll after `IO.cede`, and the twin agrees with the direct run. v3.7.1 passes program 2 by chance (mask and `IdPoll` both lost, so `poll(IO.canceled)` cancels as in the direct run).
- Program 10 (`IO.uncancelable(_ => throw e).handleErrorWith(...)`): v3.7.1 lets the throw leave `interpret` (model: rest `IO.raiseError(e)`, `Errored`); PR #4700 catches it in the region.
- Not proven: `WellFormed` for the 10 programs (they are Scala programs by construction). `PollOpaque` is stated for the v3.7.1 poll kinds; the twin adds a third kind (`DeferredPoll`), so the twin family is outside the formal clause.
- CE-0003 / PR #4710: not a local change (removes the `IOFiber` finalizer stack, adds `onCancelGraceful`, changes `ContState`), so no small twin. Plan: run the CE-0003 reproducer on a snapshot of the PR when it settles.

## Gotchas

- A `where` helper of a recursive `def` cannot see the pattern variables of the equation; use a local `let` function.
- `rfl` for "fuel `m + F` gives the same rest" needs `set_option maxRecDepth 100000` when the rest is large (twin programs 8 and up).
- The worktree hook refuses shell commands with complex quoting (`gh --jq`, heredocs with git): write scripts to the scratch directory and run them.
